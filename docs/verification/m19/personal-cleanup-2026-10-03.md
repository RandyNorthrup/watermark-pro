Eligibility requires the trusted private-workspace mapping, immutable personal creation kind, personal plan kind, the deleting user as current sole owner/member, a quiesced live user, and creation provenance belonging to that user or null. Null creation provenance is accepted only with all other proofs; a legacy positive must exercise actual foreign-key nulling, not disable immutable provenance. Known shared/historical, collaborative and other-owner scopes are preserved. Inconsistent claimed-personal proof returns `ACCOUNT_CLEANUP_PENDING` and retains credentials. The transaction repeats eligibility and checks that every recorded object key belongs to the personal namespace before destructive changes. Existing pending/cleanup keys must be valid arrays with the photo/logo cardinality and only same-namespace text keys. Malformed existing recovery records retain credentials and content instead of stranding unsafe cleanup after removal.

Cleanup uses the existing upload reservations, without another table, queue, job, key format or provider dependency. Pending producers become cleanup candidates. The already-integrated per-lease conditional R2 protocol prevents a paused producer from recreating personal payload after deletion and cleanup release. A zero-byte placeholder after a crashed initializer is a documented fence limitation, not evidence of retained personal payload. The last physical cleanup release and guarded empty-personal organization finalizer run in one D1 transaction, so a failed finalizer retains retry authority. Shared organizations cannot satisfy the finalizer.

Provider or staging failure preserves password/account rows; conditional rollback restores sign-in only if the server's deletion marker still matches. A concurrent real moderation ban is not rolled back. A lost staging acknowledgment can mean shares and metadata are already removed and keys are queued even though credentials remain; retry must safely complete without duplicate cleanup work. Earlier billing behavior conservatively suspends paid access after unsuccessful removal and requires verified reconciliation for recovery. This candidate does not promise unchanged paid access after such a failure.

Collaborative content, existing audit entries (including names/identifiers already recorded) and financial receipts remain separate records. This change neither assigns them an invented legal retention period nor erases another member's workspace. Existing browser/offline copies, third-party downloads and provider backups are not immediate physical erasure. The immutable seed client has no account-removal controls. Root is separately implementing a self-service removal card and device-data handling; its combined behavior and visual/axe evidence remain pending.
