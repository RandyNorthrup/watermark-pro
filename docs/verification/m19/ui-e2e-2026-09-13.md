## Quiet rerun and preview race

The fresh-build rerun selected the nine failed cases plus the two prerequisite
iPhone library cases required by that serial suite. It finished **10 passed and
1 failed in 7.0 minutes**, retained in `temp/ui-final-e2e-rerun.log`. Eight original
failures and both prerequisite cases passed. The remaining Android Recent work
case failed earlier than its original installation wait: after choosing a photo,
the canvas kept showing `Rendering preview` and the save action stayed disabled
until the 180-second overall deadline. That rerun did not reach this case's
offline section, so it does not independently close its original installation
failure.

The Android rerun trace at
`test-results/ui-final/recent-work-recent-work-op-dfcad-s-private-on-account-switch-android/trace.zip`
contains 2,672 captured requests across three network files and no HTTP 5xx. Its
watermark Worker script requests returned 200. The classified gate log contains
one `forwarding_failed; sdk_dispatch; fetch_failed`, but it records neither a
timestamp nor a request path. That entry cannot be assigned to this failure from
the retained evidence.

Read-only inspection identified a race in `PreviewRenderer.render()`: it reserved
its render sequence only after awaiting the initial sample photo. A real photo
could finish loading and start its first render during that wait. The older
sample operation could then resume, adopt the newly selected subject, reserve a
later sequence and invalidate the new photo's frame. The disposed old UI queue
discarded the older operation's output, while the current queue received `null`
and had no replacement frame to display. The trace shows overlapping sample
fetch and photo selection, consistent with this race, but does not record the
renderer promises themselves.

A deterministic regression in the existing `preview.browser.test.ts` reproduced
the defect using Chromium, real image decoding, the real canvas pipeline and a
controlled asynchronous engine boundary. It holds the old sample response,
selects a real photo, starts that photo's render, releases the old sample, then
finishes the real-photo render. With the original code, the assertion that the
new photo has a frame failed with **`expected null not to be null`**. This proves
the product race independently of the gate-network hypothesis; it does not claim
the trace established every scheduling detail.

The fix reserves frame ordering before awaiting the sample and verifies the
captured subject request, render sequence and disposal state before adopting a
subject or starting engine work. A stale sample now returns `null` without
invalidating the new frame. The regression also verifies the accepted frame has
the real photo's pixel dimensions and that the stale operation does not invoke
the engine. A separate disposal case verifies no engine work starts after a
pending sample is retired. No E2E assertion, timeout, retry, or gate-server
behavior changed.
